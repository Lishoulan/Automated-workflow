# 标题阶段归因诊断：候选到底在哪一步被杀光

日期：2026-09-17
脚本：`scripts/diagnose_title_stage.py`（只读缓存 + **单次** LLM 调用，可复现）
原始数据：`.runtime/title_stage_diagnose.json`、`.runtime/title_stage_diagnose_by.json`

---

## 1. 为什么做这个诊断

Phase 0.5 的云端对照实验（`docs/PHASE05_TITLE_MODEL_EXPERIMENT_20260917.md`）给出一个混合结论：

- 换成 `glm-4.6` 后，塌缩指标改善（similarity 0.338→0.242、cluster@0.5 0.646→0.450）、
  judgment 率 18%→78%；
- **但候选数没有增加（5 / 4），archetype 反而从 4 收窄到 2。**

于是留下一个必须回答的问题：**候选为什么只有 4~5 条（提示词要求 20）？**

当时的产物里只有最终候选，没有分阶段数据 —— 无法判断究竟是
（A）模型只返回了几条、（B）语义骨架去重杀掉了大半、还是（C）合规校验杀掉了大半。

诊断脚本用缓存里的**真实 `data_report` + 真实正文**重建一次 TitleAgent 调用，
并在实例级包装 `request_json` / `_dedupe_titles` / `validate_title_compliance` / `_fallback_titles`
逐阶段计数（不改动生产代码）。

---

## 2. 结果：两个独立选题，同一个模式

| | 样本 1 | 样本 2 |
|---|---|---|
| 选题 | 9秒32 机器人打破人类百米纪录 | 比亚迪玩跨界？进军人形机器人，代号"尧舜禹" |
| 标题模型 | `glm-4.6` | `glm-4.6` |
| **模型原始 titles** | **20**（＝提示词要求） | **20** |
| 模型原始 recommended_titles | 3 | 3 |
| 去重（模型侧） | 20 → 20（**杀掉 0**） | 20 → 20（**杀掉 0**） |
| **兜底产出** | **22 条** | **25 条** |
| 合并后池子 | 42 | 45 |
| 合规校验（带正文＝模型候选） | 42 次，**通过 0** | 45 次，**通过 0** |
| 合规校验（不带正文＝兜底） | 2 次，通过 2 | 2 次，通过 2 |
| 最终输出 | 20 条 | 20 条 |

**结论：三个候选都没问题 —— A 不成立、B 不成立。** 模型稳定给满 20 条，去重一条都没杀。

---

## 3. 四个被证实的具体缺陷

### D1. 兜底模板与模型候选同池竞争，且数量更多（**最严重**）

`_fallback_titles()` 产出 22~25 条硬编码填空句（`{keyword}` 套 20 个句型），
经 `_dedupe_titles(titles + fallback_titles)` **与模型的 20 条合并进同一个池子**。

实测后果（样本 2，最终输出 20 条）——约一半是硬编码模板，且它们是**逐字命中源码行**的：

| 输出标题 | 来源 |
|---|---|
| 比亚迪热度之外，谁在拿走真正订单 | `title_agent.py:387` |
| 比亚迪下一代方案已定型，谁在领跑 | `title_agent.py:369` |
| 比亚迪升温之后，先突围的不是热门公司 | `title_agent.py:376` |
| 比亚迪爆单之前，谁先卡住核心零部件 | `title_agent.py:388` |
| 比亚迪460万台：比亚迪真实进度看交付 | `title_agent.py:526` |

云端 9-17 14:38 那篇的**推荐标题**同样是兜底骨架
（`特斯拉2027：Optimus真实进度看交付`）。

⚠️ 关键：`review_service._title_candidates()` = `recommended_titles + titles`，
**只要模板进了 `titles`，它就能被 `select_auto_title` 选中并发布**，且择优按
`title_click_preference` 打分 —— **顺序救不了它，附录也不行**。
这正是 2026-09-16「零阅读模板必然胜出」缺陷的同族复发，只是换了骨架。

### D2. 合规闸 all-or-nothing：全灭时静默失效

```python
compliant_titles = [t for t in ranked_titles if self.validate_title_compliance(t, body_reference)]
if compliant_titles:          # ← 全灭时这个分支不执行
    ranked_titles = compliant_titles
```

实测 42/42、45/45 全灭 ⇒ `if` 不成立 ⇒ **整道闸被跳过，一条都没过滤**，且没有任何日志。
也就是说这道闸在当前真实数据分布下**要么完全不生效、要么严厉裁剪**，行为不可预测。

### D3. 兜底不过「正文一致性」，模型候选要过全套

`_fallback_fact_titles()` 第 541 行调用 `self.validate_title_compliance(title)` —— **不传 `body_text`**，
于是 `_has_concrete_hook` 与 `check_editorial_integrity` 两道闸对兜底完全跳过。

诊断输出直接印证了这个不对称：

```
合规校验（共 47 次调用）
  带正文（模型候选）: 45 次，通过 0
  不带正文（兜底）  :  2 次，通过 2
```

**兜底天然更容易存活，也就更容易被选中。** 这是结构性的，不是参数问题。

### D4. `_has_concrete_hook` 的元素提取过松

`_extract_concrete_elements()` 把 `\d+` 单字数字也算「具象元素」（如 `9`、`10`），
导致模型候选几乎必然挂在这道闸上（42/42、45/45），从而触发 D2 的静默失效。

## 4. 已修的（本轮，零风险，行为可预期）

| 修复 | 位置 | 说明 |
|---|---|---|
| 兜底拼接病句守卫 | `title_agent._has_repeated_anchor()` | 锚定词（公司/主题标签/次要词）在兜底标题里出现 ≥2 次即丢弃该条。实测拦掉「比亚迪的比亚迪生意，真正的收入来自什么」「比亚迪460万台：比亚迪真实进度看交付」这类会进入候选池的病句。样本 2 兜底 25 → 15 条 |
| 分阶段计数日志 | `title_agent.run()` | 固定打印 `模型原始 → 去重后；兜底；合并；合规通过；输出`，并在合规闸全灭时打 WARNING。此前这三段完全不可观测 |

回归：`tests/test_daily_topic_quality.py::test_fallback_titles_never_repeat_the_same_anchor`。

## 5. 未动、待裁决的（**需要你决定**）

以下三项会改变「发出去的标题」，属发布行为决策，本轮**没有动**：

1. **D1 候选池策略**：硬编码模板是否还该与模型候选同池？
2. **D2 闸门语义**：合规闸全灭时该「静默放行」还是「保底留 N 条」？
3. **D3 对称性**：兜底是否应接受与模型候选相同的正文一致性校验？

风险点必须说清：`select_auto_title` 若挑不出任何通过闸门的标题，
`app_service` 会把该 attempt 判为 `qualifies = False` 并换下一个选题 ——
**兜底候选正是「至少有一条能过闸」的保险**。贸然撤掉兜底，可能把「发一篇烂标题」
变成「当天不发」（即项目里反复出现的「单个候选否决整天」缺陷族）。

---

## 6. 限制

- 诊断只覆盖 **2 个选题**，样本来自本地 `cache/`，不能替代云端真实分布。
- 单次 LLM 调用有随机性：模型返回条数可能波动（但两次都恰好 20，与提示词一致）。
- 本诊断**与 CTR 无关**。它只解释「候选池里装的是什么」，不解释阅读量。

---

## 7. 对 Phase 1 计划的修正

Phase 0.5 结束时我建议的下一步是「**语义去重 + 塌缩触发二次生成**」。
本诊断**否定**了这个方向：

- **语义去重不需要做**：`_dedupe_titles` 在真实样本上杀掉 **0 条**。
- **二次生成不需要做**：模型已经给满 20 条且足够多样；问题在候选池被模板稀释。

正确方向是：**先修候选池来源与闸门语义（D1/D2/D3），再谈生成侧**。
这与项目已记录的核心教训一致 —— **闸门是事后过滤，候选的来源与顺序才是决定性的。**
